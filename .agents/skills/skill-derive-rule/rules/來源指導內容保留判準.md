# Rule 1 - 來源內容若是判斷清單，RuleFile 必須保留清單結構

- Level: `MUST`
- 若來源 step 或外部參考內容包含 taxonomy、checklist、掃描維度、候選問題分類或多層判斷清單，展開 RuleFile 時必須保留其清單結構。
- 可以調整 wording 以符合目標 skill 語境，但不可把多層清單壓縮成單一抽象條列。
- 若某些來源項目因目標 skill 邊界而不適用，必須明確說明刪除或 defer 的理由。

## Good Example

- 這個例子是好的，因為它把來源 taxonomy 轉成目標 RuleFile 的完整掃描項。

````md
來源：
- Functional Scope & Behavior
- Domain & Data Model
- Interaction & UX Flow
- Non-Functional Quality Attributes

RuleFile：
- 保留四個分類
- 每個分類底下保留其子項
- 補上目標 spec 語境的說明
````

## Bad Example

- 這個例子是壞的，因為它把清單結構壓縮成一句話，導致後續 agent 無法重演原判斷。

````md
RuleFile：
- 系統性掃描需求缺口
````

# Rule 2 - 來源內容若是長篇 prompt surface，預設保留語意密度

- Level: `SHOULD`
- 若來源內容靠長篇說明、例外條件、排序規則或 Good/Bad Example 產生效果，展開 RuleFile 時應保留足夠語意密度，而不是追求最短文字。
- RuleFile 可以比主 SOP 長；主 SOP 精簡的目的，是把細節委派到正確資源，不是讓被委派資源也失去細節。
- 只有在某段來源內容與目標 step 無關、或會造成錯誤 handoff 時，才應摘要或刪除。

## Good Example

- 這個例子是好的，因為它承認 RuleFile 可以承載長篇判準。

````md
主 SOP：
- THINK 讀取 `rules/spec高影響缺口掃描與提問排序判準.md`

RuleFile：
- 約 150 行，包含分類清單、篩選條件、排序規則與 Good/Bad Example
````

## Bad Example

- 這個例子是壞的，因為它把所有模組都壓短，犧牲原本 prompt 的判斷力。

````md
決策：
- 為了簡潔，每份 RuleFile 最多 20 行
````

# Rule 3 - 展開結果必須能在不回讀來源的情況下重演核心能力

- Level: `MUST`
- 完成 RuleFile 後，應檢查執行者只讀目標 skill 與新 RuleFile 時，是否能重演來源內容的核心判斷。
- 若仍必須回頭讀原始來源才知道分類、子項、排除條件或排序方式，表示 RuleFile 沒有完成承接。
- 若來源能力只被部分承接，RuleFile 必須明示承接範圍與 deferred 範圍。

## Good Example

- 這個例子是好的，因為新 RuleFile 自身已足以引導需求缺口掃描。

````md
檢查：
- 不讀 Speckit 原檔，只讀新 RuleFile
- 仍知道要掃描 NFR、整合依賴、術語一致性與 Completion Signals
- 仍知道 Partial / Missing 要建立候選問題
````

## Bad Example

- 這個例子是壞的，因為 RuleFile 只留下來源名稱，實際執行仍要回頭讀原文。

````md
RuleFile：
- 參考 Speckit clarify 的 taxonomy
````
