# Rule 1 - 編排前必須辨識來源能力是否依賴高指導面積

- Level: `MUST`
- 在把既有 SOP、外部 skill、prompt 片段、taxonomy、checklist 或範例轉成新 skill 模組前，必須先判斷該來源能力是否依賴高指導面積才能產生效果。
- 若來源內容包含多層分類、逐項掃描清單、範例密集判準、候選問題集合、格式化輸出骨架或高風險防呆條件，應標記為高指導面積來源。
- 高指導面積來源不可只被摘要成抽象原則，後續 derive rule / template 時必須保留足以重演原能力的語意密度。

## Good Example

- 這個例子是好的，因為它先辨識 taxonomy 本身就是能力核心，而不是把它當成可刪的說明文字。

````md
來源能力：
- Speckit clarify 的需求缺口 taxonomy
- 包含功能範圍、資料模型、UX、NFR、整合、邊界情況、取捨、術語、完成訊號與 placeholder 掃描點

判斷：
- 高指導面積來源
- derive rule 時必須保留分類與子項清單
````

## Bad Example

- 這個例子是壞的，因為它把 taxonomy 視為可以被一句話取代的背景說明。

````md
來源能力：
- 一整段需求缺口 taxonomy

判斷：
- 摘要成「系統性掃描需求缺口」即可
````

# Rule 2 - 模組化後必須保留來源能力的等價提示面積

- Level: `MUST`
- 若來源能力被判定為高指導面積，工程化後的 RuleFile、template 或 script 說明必須保留等價提示面積，讓後續 agent 不需要回讀原始來源也能重演同等品質。
- 等價提示面積不要求逐字複製，但必須保留原本會影響判斷品質的分類、子項、排序邏輯、排除條件與常見失誤。
- 不可把「主 SOP 精簡」誤套用成「被委派資源也要短」；精簡控制平面與保留模組語意密度是兩件事。

## Good Example

- 這個例子是好的，因為它讓主 SOP 保持短，但在 RuleFile 中完整保留掃描清單。

````md
主 SOP：
- READ 讀取 `rules/spec高影響缺口掃描與提問排序判準.md`

RuleFile：
- 明列 10 個 taxonomy 類別
- 每類保留 2 至 5 個掃描子項
- 說明如何標記 Clear / Partial / Missing
- 說明何時建立 candidate question opportunity
````

## Bad Example

- 這個例子是壞的，因為它雖然符合單一溯源，卻把單一溯源中的內容壓縮到不足以執行。

````md
主 SOP：
- READ 讀取 `rules/spec高影響缺口掃描與提問排序判準.md`

RuleFile：
- 系統性掃描功能、資料、流程與成功標準
````

# Rule 3 - 編排提案必須說明來源能力保留策略

- Level: `MUST`
- skill engineering plan 必須針對高指導面積來源說明保留策略，至少交代來源能力、保留位置、保留粒度，以及哪些內容可以安全摘要或刪除。
- 若提案決定濃縮來源內容，必須說明為什麼濃縮後仍能重演原能力；否則應視為提案不完整。
- 若來源內容的價值來自長篇 prompt surface，預設應保留足夠篇幅，而不是要求使用者事後指出缺失。

## Good Example

- 這個例子是好的，因為它在提案階段就說清楚 taxonomy 要如何被完整承接。

````md
來源能力保留策略：
- 來源：Speckit clarify taxonomy
- 保留位置：`rules/spec高影響缺口掃描與提問排序判準.md`
- 保留粒度：保留所有分類與子項；只把 Speckit hook 與 CLI 執行細節刪除
- 不保留內容：與本專案 skill runtime 無關的 extension hook 語法
````

## Bad Example

- 這個例子是壞的，因為它只說要 derive rule，沒有交代來源內容會如何不失真地轉移。

````md
步驟決策：
- `需求缺口掃描`：derive rule
````

# Rule 4 - 驗證時必須重演來源能力是否仍可達成原判準

- Level: `SHOULD`
- 完成修改後，應用一個代表性案例重演新 workflow，檢查高指導面積來源在新 skill 中是否仍會觸發等價判斷。
- 驗證不能只看檔案是否被引用，也要檢查內容是否足以讓 agent 找到原本會找到的缺口。
- 若 evaluator 或人工重演發現新模組無法帶出來源能力的核心清單、分類或判斷步驟，應回到編排或 rule 內容修正。

## Good Example

- 這個例子是好的，因為它用具體 spec 重演 taxonomy 掃描是否仍然有效。

````md
驗證案例：
- 使用 PVP 1A2B spec

期望新 workflow 至少能掃出：
- 先手規則
- 斷線處置
- 同步延遲門檻
- 對外部服務/協議假設是否缺失
````

## Bad Example

- 這個例子是壞的，因為它只驗證引用沒有斷，沒有驗證能力是否仍存在。

````md
驗證：
- analyze_skill_references 沒有 missing refs
- 因此來源能力保留成功
````
