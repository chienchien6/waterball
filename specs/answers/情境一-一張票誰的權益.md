# 情境一｜一張票，誰的權益？

## 1. 購買人、持有人、訂單、票券與贈品兌換紀錄

- **購買人**：建立訂單並完成付款的人，是訂單上的原始購買角色。以本題為例，甲是購買人。
- **訂單**：記錄購買交易及付款狀態。一筆訂單可以包含多張票券；訂單付款完成後，所含票券才符合本題的已付款條件。
- **票券**：代表一項可獨立使用的權益，應有自己的票券 ID、所屬訂單、有效狀態及目前持有人。票券可以轉贈，因此目前持有人不一定是購買人。
- **目前持有人**：目前有權操作該張票券的人。甲將 T1 轉贈給乙後，T1 的購買人仍是甲、目前持有人改為乙；同一訂單中的 T2 仍由甲持有。轉贈只更新 T1 的目前持有人，不改變訂單購買人，也不影響 T2。
- **贈品兌換紀錄**：記錄哪張票券兌換了哪一種贈品、由誰操作及兌換時間。紀錄應關聯票券 ID 與贈品種類，並保留實際核銷者及時間供追蹤。

因此，資料與操作上應分開記錄訂單的購買人，以及每張票券的目前持有人。核銷時依目前持有人判斷操作者資格，不應因為票券曾被轉贈而改寫原購買人資料。

## 2. 重要業務規則與模型

我認為重要的規則是：**只有已付款且有效票券的目前持有人，才能使用該票券核銷贈品；同一張票券對同一種贈品最多核銷一次，轉贈不會重置核銷次數。**

我會將票券狀態與目前持有人放在票券模型中，將付款狀態放在訂單模型中，並以贈品兌換紀錄表示核銷事實。兌換紀錄以 `(ticket_id, gift_type)` 作為唯一鍵或唯一性約束，確保同一張票不能重複核銷同一種贈品；不同票券或不同贈品種類則分別判斷。實際核銷者可另存為 `redeemed_by`，但不納入唯一鍵，因為核銷權益跟著票券與贈品種類走，不跟著持有人走。

贈品核銷與入場驗票是不同操作，應有各自的紀錄與規則；是否核銷贈品不能用來推斷是否已入場，反之亦然。

## 3. 前台顯示與後台核銷如何使用規則

前台可以根據目前資料顯示票券是否可兌換，提供使用者操作提示；但這個結果只是查詢當下的狀態，不能作為核銷成功的保證。狀態可能在顯示後改變，也可能有兩個櫃台或請求同時嘗試核銷。

因此，後台執行核銷時必須在交易中重新確認請求者是票券目前持有人、訂單已付款、票券仍有效，且該 `(ticket_id, gift_type)` 尚未核銷，之後再建立兌換紀錄。我會先開始交易，再用 `SELECT ... FOR UPDATE` 鎖住該票券資料列，使同一張票的並行核銷依序處理；核銷紀錄表再設定 `UNIQUE (ticket_id, gift_type)`，作為資料庫層防止重複核銷的最終防線。若請求等待鎖定後發現該贈品已核銷，或新增時觸發唯一性限制，便回覆 HTTP `409 Conflict`，表示此票券已核銷過此種贈品。前台的可兌換提示只是當下狀態，不能取代後台的資格重驗與原子性寫入。
